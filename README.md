# Cyber Insurance Gap Analysis

A wedge MVP for MSPs: walk an SMB client through a cyber-insurance readiness
questionnaire, flag which answers will pass or fail insurer expectations, and produce a
brandable gap report the MSP can hand the client.

Every answer is stored as a structured evidence record scoped to a `client_id`, so the
same data supports a multi-client console later without a migration.

## Run it

```bash
npm install
npm run sample     # seeds a demo client and writes samples/sample-gap-report.html
npm start          # http://localhost:3000
```

Requires Node 22.5+ (it uses the built-in `node:sqlite`). Express is the only
dependency. The database is a single file at `data/gap-analysis.db`; `npm run reset`
deletes it.

Open `samples/sample-gap-report.html` in a browser to see the output an MSP would hand
a client — it is a standalone file with the stylesheet inlined, generated by the same
code path the web app uses.

| Command | What it does |
|---|---|
| `npm start` | Runs the app on port 3000 (`PORT` to override) |
| `npm run dev` | Same, restarting on file changes |
| `npm run sample` | Regenerates the sample report and seeds the demo client |
| `npm run reset` | Deletes the local database |

## Editing the control definitions

**`config/controls.js` is the file you edit.** It holds the questionnaire, the
pass/fail rules, and the plain-language gap and fix copy. Nothing under `src/` knows
that MFA or backups exist — the app only knows how to walk that structure, so swapping
in a real insurer questionnaire means editing that file (or adding a sibling and
pointing the import at it), not touching application logic.

The file's header comment documents the full schema. In short, each control is:

```js
{
  id: 'MFA_COVERAGE',          // stable key — evidence records are keyed on it
  domain: 'Identity & Access', // section heading
  title: 'Multi-factor authentication',
  weight: 20,                  // share of the 100-point score; weights sum to 100
  severity: 'critical',        // a failing 'critical' control caps the verdict
  insurerContext: 'Why carriers ask…',
  questions: [ /* … */ ],
}
```

and each question carries its own rule and its own copy:

```js
{
  id: 'mfa.email',
  prompt: 'Is MFA required for every employee email account?',
  type: 'choice',                                   // or 'number'
  options: [{ value: 'all', label: 'Yes — every user' }, /* … */],
  evaluation: { pass: ['all'], partial: ['most'] }, // anything else fails
  outcomes: {
    partial: { gap: 'consequence in plain English', fix: 'what to do' },
    fail:    { gap: '…', fix: '…' },
  },
}
```

Numeric questions use comparators instead of value lists:
`evaluation: { pass: { gte: 98 }, partial: { gte: 90 } }` (also `gt`, `lte`, `lt`, `eq`).

Two rules worth knowing when you edit:

- A control's status is the **worst** status among its questions, but its **score** is
  the average — so one failing question marks the control failed without zeroing the
  partial credit earned elsewhere in it.
- An unanswered question is `unknown`, not `fail`. It scores as zero but is reported
  separately, because "nobody here knows" is its own finding.

Bump `QUESTIONNAIRE.version` when you change anything. Every assessment stores the
version it was answered against, and reports render from a frozen snapshot, so an old
report keeps rendering as it was issued.

### Rebranding the report

`config/branding.js` — company name, tagline, logo (URL or `data:` URI), accent colour,
contact details, and the footer disclaimer. That is the whole theming surface.

## Data model

SQLite, four tables, `client_id` on every row that has one:

- **`clients`** — the SMB being assessed.
- **`assessments`** — one questionnaire run, stamped with questionnaire id + version.
- **`evidence_records`** — **one row per question answered**: the control, the answer,
  pass/fail, the gap and fix text, who recorded it, when, and from what source
  (`questionnaire`, `sample_seed`, and later `integration:okta` and friends). This is
  the ledger; it is indexed on `(client_id, control_id, recorded_at)` so a cross-client
  query like "every client failing MFA" is a single `WHERE`.
- **`assessment_results`** — the frozen score, band, and full report snapshot.

Every read and write in `src/db.js` takes `clientId` as its first argument and throws
without one. Routes never touch the raw `:clientId` parameter — `app.param` resolves it
through the access check once and hands routes `req.client`, so a new route cannot
forget to scope its query.

JSON endpoints expose the ledger directly:

```
GET /clients/:clientId/assessments/:assessmentId/evidence.json
GET /clients/:clientId/controls/:controlId/history.json
```

## Scoring

Each control contributes `weight × (average question factor)` where pass = 1,
partial = 0.5, fail and unknown = 0. The total is normalised to 100 and lands in a band:

| Band | Condition |
|---|---|
| Insurance ready | ≥ 85 and no failing critical control |
| Insurable with conditions | ≥ 65 and no failing critical control |
| Not yet insurable | < 65, **or** any critical control failing at any score |

The critical override is deliberate: a business can score well overall and still be
uninsurable because one precondition is missing. The sample report is exactly that case
— 60/100 with good hygiene throughout but untested backups.

## Deliberately not built

Per the pilot scope: no live integrations with identity/EDR/backup systems (manual
input only), no real auth (`src/auth.js` is a stub that returns a fixed operator and
allows every client), no billing, no white-label theming engine beyond the branding
config, and no multi-client console — though the data model is already shaped for one.

## Layout

```
config/
  controls.js       ← the questionnaire, rules, and plain-language copy (edit this)
  branding.js       ← company name, logo, colours, disclaimer
src/
  server.js         ← Express routes
  db.js             ← schema + tenant-scoped queries
  evaluate.js       ← pure scoring engine, knows nothing about specific controls
  auth.js           ← stub
  views/            ← server-rendered HTML
public/styles.css   ← shared by the app and the standalone report
scripts/
  generate-sample.js
  reset-db.js
samples/
  sample-answers.json      ← edit and re-run `npm run sample` to try other profiles
  sample-gap-report.html   ← the artifact an MSP hands a client
  sample-evidence.json     ← the same run as structured evidence records
```
